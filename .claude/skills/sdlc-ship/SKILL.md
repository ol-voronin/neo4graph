# /sdlc-ship — від спеки до PR

Ти диригент в основній сесії. Субагенти не бачать цієї розмови: у кожне завдання клади спеку, задачу й правила з `CLAUDE.md` проєкту.

## 0. Перевір вхід
Шукай у `docs/specs/` спеку зі `Статус: затверджено` (кілька — спитай, яку). Знайшов — переходь до плану.

Спеки немає або вона не затверджена — **не зупиняйся**, зроби коротку спеку тут же:
1. Задача є в повідомленні (`/sdlc-ship поправити посилання…`) — бери її. Немає — одне питання: «Що робимо?»
2. Мала задача (1–2 файли, без нових даних і прав доступу) — експрес-спека: Навіщо, Обсяг, 2–4 критерії приймання. Більша — пройди скіл `/sdlc-spec` повністю.
3. Запиши `docs/specs/<YYYY-MM-DD>-<фіча>.md`, покажи в 5–8 рядках і спитай «затверджуєш?».
4. Після «так» допиши `Статус: затверджено <дата>` і йди далі. Без «так» код не пишемо.

## 1. План (лише читання)
Розбий спеку на 1–5 задач. Для кожної: що змінюється, де, як перевірити, хто робить (`frontend-dev` / `backend-dev`). Запиши в `docs/specs/<…>.plan.md`. Покажи власнику; великий план (>5 задач) — спитай.

## 2. Build
Кожну задачу — окремому агенту (`frontend-dev` або `backend-dev`, вони в worktree). Незалежні задачі — паралельно, залежні — по черзі. Кожен повертає команду збірки й вивід.

## 3. Гейт збірки
Злий гілки worktree у робочу гілку `claude/<фіча>`, запусти збірку й тести самостійно. Червоне — назад агенту з виводом помилки. **Не більше 2 повторів**, далі зупинка й питання власнику.

## 4. Verify — паралельно, свіжий контекст
- `tester` — критерії приймання й Playwright smoke
- `reviewer` — код проти спеки, баги, безпека
- `design-auditor` — якщо змінювався UI
Блокер від будь-кого — назад у Build (рахується в ті самі 2 повтори).

## 5. PR
Push гілки `claude/<фіча>` (не main), PR з описом: посилання на спеку, що зроблено, звіти tester / reviewer / design-auditor коротко, превʼю-адреса Vercel. Перевір, що превʼю зібралось (Vercel MCP або `gh pr checks`).

## 6. Зупинка
Прод — лише через `/sdlc-release`, який запускає власник.
